## Claude: эндпоинт использования

Запрос идёт из контекста залогиненной страницы claude.ai (так обходится проверка Cloudflare): `fetch('/api/organizations/{org}/usage', { credentials: 'include' })`.
Идентификатор организации берётся из `/api/organizations` (первая с возможностью `chat`).

**Ожидаемая форма ответа** (по сторонним проектам, не подтверждена; поля `utilization` в процентах 0–100, `resets_at` — ISO-время):

```json
{
  "five_hour":        { "utilization": 34.0, "resets_at": "2026-11-03T12:00:00+00:00" },
  "seven_day":        { "utilization": 41.0, "resets_at": "2026-11-07T07:00:00+00:00" },
  "seven_day_opus":   null,
  "seven_day_sonnet": { "utilization": 12.5, "resets_at": "2026-11-07T07:00:00+00:00" },
  "extra_usage":      { "is_enabled": false, "monthly_limit": null, "used_credits": null, "utilization": null }
}
```

Что проверить при спайке:

- [x] форма ответа совпала с адаптером (`parseUsage`), `utilization` — именно проценты, а не доли (82 и 55 совпали с `limits[].percent` в том же ответе). Сверено со страницей Usage в Claude Desktop (2026-10-31, ~23:00 MSK): сессия 85% и неделя 55% в виджете и на странице совпали, сброс 01:40 и воскресенье 07:00 совпали с «сброс через 2ч 40м» и «8ч 00м» в виджете (допуск из плана ≤ 1 п.п. выдержан);
- [x] срезы по моделям: `seven_day_sonnet` и `seven_day_opus` на тарифе Pro равны `null`. Зато в ответе есть `seven_day_breakdown.rows`: 4 строки с долями, в сумме 100 (31, 12, 57, 0), то есть расход недели поделён **по продуктам, а не по моделям**. Спайк 19:57 UTC показал: Claude Code 32, Чаты 12, Cowork 56, Другое 0 (и 31 / 12 / 57 / 0 за 11 минут до этого). Это доли от израсходованного, а не от лимита (сумма 100 при недельных 55%); в абсолютных пунктах лимита выходит примерно 17.6 / 6.6 / 30.8. Окно разбивки совпадает с недельным (`window_started_at`, `as_of`). Адаптер этот блок пока не читает;
- [x] допустимая частота опроса: три запроса подряд без ошибок, 276 / 281 / 329 мс; для опроса раз в 60 секунд запас большой;
- [x] поведение Cloudflare: запросы изнутри страницы проходят без проверки (HTTP 200);
- ещё в ответе: `limits[]` (`kind: session` / `weekly_all`, `percent`, `severity`, `resets_at`, `is_active`) повторяет те же окна; недельный сброс приходится на воскресенье 04:00 UTC (07:00 по UTC+3); `spend` и `extra_usage` отключены;
- [x] вход переживает перезапуск: после закрытия и повторного запуска виджета спайк (19:59 UTC) снова получил 200 без повторного входа, `sessionKey` по-прежнему со сроком 28 дней; сессионных cookie нет;
- [ ] продление: сессия не истекает, пока виджет работает (опрос + перезагрузка страницы раз в час).

Если путь или поля отличаются, меняется **только** `packages/app/src/providers/claude.ts` (константы `CLAUDE_USAGE_PATH`, `ENTRIES`, `PCT_KEYS`, `RESET_KEYS`).

## Поведение 5-часового окна

По стороннему обзору, окно стартует с первого сообщения и сбрасывается через 5 часов. Для вас это правило: открывать окно первым сообщением в начале блока
(первое сообщение около 10:00 закрывает окно около 15:00, а второе окно покрывает 15:00–20:00 целиком). Подтверждение: отправьте сообщение сразу после сброса
и сравните `resets_at` до и после; запишите результат здесь.

## Модель, режим и время задачи в Claude Desktop

Эндпоинт этих данных не отдаёт. Порядок проверки — от менее инвазивного к более:

| № | Способ | Модель и режим | Время задачи | Риски | Результат |
| --- | --- | --- | --- | --- | --- |
| 1 | Разговоры claude.ai через собственную сессию виджета | возможно, в данных разговора | возможно, по времени создания сообщений | ничего не трогает в приложении; запросы неофициальные | _не проверено_ |
| 2 | UI Automation окна Claude Desktop, только чтение | подпись меню модели, усилия, переключатель Extended | индикатор «Thinking» с таймером | Chromium строит дерево доступности по запросу, приложение тратит больше памяти и процессора: замерить | _не проверено_ |
| 3 | Отладочный порт Claude Desktop | точно, через DOM | точно, по потоку ответа | любой локальный процесс получает доступ к коду внутри приложения; нужен запуск с флагом; Microsoft Store усложняет запуск; согласие дано при условии, что производительность не пострадает | _не проверено_ |
| 4 | Недельные срезы по моделям из эндпоинта | грубо: Sonnet и Opus | нет | зависит от тарифа | _см. проверку эндпоинта_ |
| 5 | Ручная отметка | да | кнопка «Задача» | требует действий | **работает** |

Не берётся чтение локальных данных приложения: они лежат в IndexedDB, заблокированной во время работы, а у установки из Microsoft Store — ещё и в виртуализированной папке.

Замер нагрузки для способов 2 и 3: откройте Диспетчер задач, запишите CPU и память Claude Desktop 5 минут без инструмента и 5 минут с ним; перенесите цифры сюда.

## Codex в ChatGPT Desktop (без реализации)

Спайк ищет `~/.codex/sessions/**/rollout-*.jsonl` (или `$CODEX_HOME/sessions`), читает **только** строки с `rate_limits` и пишет обезличенный образец.
Ожидаемая форма (по сторонним источникам; подтверждается спайком):

```json
{ "timestamp": "…", "type": "event_msg",
  "payload": { "type": "token_count", "info": { "total_token_usage": { "total_tokens": 1500 } },
    "rate_limits": { "plan_type": "plus",
      "primary":   { "used_percent": 18.0, "window_minutes": 300,   "resets_at": 1793000000 },
      "secondary": { "used_percent": 27.0, "window_minutes": 10080, "resets_at": 1793400000 } } } }
```

Модель и режим берутся из `turn_context` (`payload.model`, `payload.effort`), границы задач — из `task_started` / `task_complete`. Окна различаются по `window_minutes`, а не по имени
`primary` / `secondary`: у Plus есть 5-часовое и недельное, у Pro пятичасового нет, у части Plus-аккаунтов пятичасовое окно пропало.

Облачный Codex в локальных логах может не отражаться; использование [делится на локальное и облачное](https://help-lb.openai.com/en/articles/11369540), и оба вида
[расходуют одно 5-часовое окно](https://www.jdhodges.com/blog/how-to-check-codex-usage-chatgpt-plus/). Отдельно проверяются процент на странице использования и список облачных задач через вход в ChatGPT.

- [x] rollout-логи лежат в `~/.codex/sessions` (на машине пользователя найдено 109 файлов, спайк 2026-10-31)
- [x] имена полей `rate_limits` совпали с адаптером: `plan_type`, `primary` / `secondary` с `used_percent`, `window_minutes`, время сброса; на тарифе Plus есть оба окна (300 и 10080 минут)
- [x] у записей есть `limit_id` (встретился `premium`), `credits` (`has_credits`, `unlimited`, `balance`), `individual_limit`, `spend_control_reached`; **последняя запись может быть с `primary: null`, `secondary: null`** — такие записи пропускаются, берётся ближайшая с окнами (проверено тестом на обезличенной записи)
- [x] основной лимит Codex — корзина `limit_id: codex` (тариф Plus: 5 часов = 300 минут и неделя = 10080 минут); `premium` — отдельная корзина без окон (`primary`/`secondary` равны null, есть только `credits`). Спайк 2026-10-31: `codex` 5ч 50%, неделя 100%
- [x] окно с прошедшим временем сброса считается сброшенным. В образце спайка 5-часовой сброс (17:15 UTC) наступил раньше самого спайка (19:46 UTC), то есть последняя запись лога давно устарела: показывать «50%» нельзя. Коннектор отдаёт 5ч = 0% без времени сброса (окно откроется первым сообщением), а недельное окно после сброса — 0% и следующий сброс по той же недельной сетке (тест на стареющие записи)
- [x] приложение ChatGPT Desktop — это пакет `OpenAI.Codex` (`ChatGPT.exe`, запускает `codex.exe`); все rollout-файлы на машине записаны с `originator = Codex Desktop`, то есть лимиты берутся из логов именно ChatGPT Desktop
- [x] живая проверка коннектора 2026-11-01: читаются 8 свежих файлов (хвосты), первое чтение 28 мс, повторное 9 мс при 517 МБ логов; последняя запись корзины `codex`: тариф Plus, 5ч 50% (сброс прошёл), неделя 100% (сброс 2026-11-05 18:35 UTC); разобрано 13 задач с моделями и режимами
- [ ] чем отличается видимость облачных задач (страница использования, список задач)

Обезличенные образцы строк лежат в `packages/app/src/providers/fixtures.ts` и используются в контрактных тестах (`packages/app/test/providers.test.ts`).
